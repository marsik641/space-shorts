# Общая очередь Blender

Независимые чаты **ставят задания**, а не запускают Blender сами. Очередь выбирает ПК, ждёт ресурс и продолжает
после закрытия чата. Общение чатов и ручной запуск каждого шота не нужны. Клиент — обычный CLI с JSON-статусом,
без MCP-сервера и внешних зависимостей. Python 3.10+; для звука используется существующая `.venv`.

## Команды для чата

Из своей рабочей копии:

```bash
# Превью всех шотов: четыре кадра на шот, 50%, затем контактный лист.
python tools/render_queue.py submit preview episodes/<ep>/episode.json --with-tts

# Быстрая проверка конкретного шота (без озвучки).
python tools/render_queue.py submit preview episodes/<ep>/episode.json --shots v2 --frames 1,240 --pct 25 --samples 4

# Только после одобрения пользователем сценария, превью и параметров финала.
python tools/render_queue.py submit final episodes/<ep>/episode.json --approved 'ок пользователя, дата и ссылка/контекст чата'

python tools/render_queue.py status
python tools/render_queue.py status --json
python tools/render_queue.py pause JOB      # закончить текущую порцию, затем ждать
python tools/render_queue.py resume JOB
python tools/render_queue.py cancel JOB     # остановить только процесс этого задания и его дочерние процессы
python tools/render_queue.py retry JOB      # повторить неуспешный шаг из того же снимка
python tools/render_queue.py retry JOB --rerender-shots v1  # после удаления плохих кадров — вернуться к рендеру
python tools/render_queue.py accept JOB     # только после просмотра PNG QA и мастера
```

В старой рабочей копии файла очереди может ещё не быть. Вызывай **скрипт из основной копии**, передавая свой
`episode.json` (относительно текущего каталога или абсолютным путём). Например, из `out/w8`:

```bash
python ../../tools/render_queue.py submit preview episodes/ep008_kelt9b/episode.json --with-tts
```

Название папки бери из своей копии, не из примера. Очередь и её worker находятся в `out/q` основной git worktree;
эпизод, библиотека сцен и обычные ассеты фиксируются из **той копии, где лежит переданный episode.json**.
Служебные шлюзы очереди и QA берутся из версии вызываемого клиента. Файлы `.venv` и веса TTS заново не скачиваются.

Обычный `submit` сам будит фоновый worker (Windows: `pythonw` через Планировщик, без окон, от текущего пользователя).
Worker также запускается при следующем входе текущего пользователя в Windows; после аварийного завершения
Планировщик делает до трёх перезапусков с интервалом в минуту. Если песочница чата
не позволяет зарегистрировать/запустить worker, само задание очереди сохраняется; агент повторяет `start` вне
песочницы с обычным механизмом разрешений среды. Уже работающий worker принимает последующие задания через базу.
`--no-start` только сохраняет задание;
если worker уже работает, он всё равно может его подобрать. Это не замена `pause`.

## Что происходит

1. Задание получает короткий id и отдельный снимок в `out/q/<JOB>/`: код, эпизод, ассеты, собственные результаты.
   Следующие правки `spacekit` и эпизодов в чатах не меняют этот снимок. Большие веса TTS связаны hardlink и
   считаются неизменяемыми: заменять файл можно, редактировать его содержимое во время работы нельзя.
2. SQLite резервирует шаг одной транзакцией. На каждом ПК блокировка ОС сериализует Blender, TTS, музыку,
   сведение, сборку и QA. `out/RENDER.lock` сохраняется для старых инструментов; существующий чужой lock или
   любой работающий `blender.exe` блокирует запуск. Неизвестный старый lock автоматически не удаляется.
   На Windows дерево каждого шага помещается в отдельный Job Object до запуска начального потока:
   отмена или авария исполнителя завершает и потомков, без зависимости от `taskkill`.
   Во время работы запрет сна действует на рендер-ПК и на координаторе, ожидающем remote; в пустой очереди снимается.
3. `auto` предпочитает свободный rinat-pc. Если он занят/недоступен — использует этот ПК. Первый шаг рендера
   закрепляет ПК за заданием; все его шоты остаются на этой машине. `--target local|remote` задаёт ПК явно.
   Настройки SSH — `out/remote.json` основной копии, как раньше. На удалённом ПК нужны существующие Blender,
   Python и ssh; два новых файла транспорта очередь загружает сама.
4. Превью имеют приоритет **100**, финалы — **0**; внутри приоритета FIFO. `--priority N` меняет приоритет при
   постановке. Финал рендерится порциями **120 кадров** (`--chunk N`). Между порциями могут пройти превью другого
   ролика. Текущий кадр/порция не прерывается ради превью. Сборка сцены повторяется на каждой порции: это цена
   меньшего ожидания; увеличить `--chunk`, если важнее пропускная способность.
5. `final`: check_episode → кадры → framecheck → TTS (OVERRUN считается ошибкой) → своя музыка → mix → build_edit →
   assemble → машинный QA → release. Cue-лист должен быть подготовлен и согласован по превью **до постановки**;
   очередь не меняет его автоматически. `publish_en.md` тоже готовится заранее и фиксируется в снимке.
6. Готовые результаты появляются в обычном `out/<ep>/` исходной копии; мастер и `publish_en.md` — в `release/`.
   Они доступны и в снимке. В пределах одного диска используются hardlink, без второй копии гигабайт кадров.
   Монтажный JSON возвращается в `episodes/<ep>/`, только если исходники эпизода не изменились за время работы.
   Состояние финала — **needs_review**: машинные проверки прошли, теперь агент смотрит PNG/мастер и делает `accept`.
   Само наличие файлов в `release/` не означает, что визуальная проверка выполнена.

Пока задача выполняется, её кадры и все логи доступны по `snapshot` из `status --json`.
Для финала логи шотов — `<snapshot>/out/logs/<ep>/render_<shot>.log`, для превью —
`<snapshot>/out/<ep>/9x16/logs/prev_<shot>.log`. Остальные логи — `<snapshot>/out/queue_*.log`.
`worker.log` и состояние подключения к удалённому ПК — в общей `out/q/`.

## Ошибки, правки и перезапуск

- Неуспешное задание получает `failed`; следующее выполняется автоматически. Исправил временный сбой среды —
  `retry JOB`. Пройденные шаги не повторяются; незаконченная порция докачивается, обрезанные PNG удаляются перед
  повтором. Framecheck FAIL требует разбора кадров и удаления плохих кадров **в снимке** (для remote — и там).
  Затем `retry JOB --rerender-shots v1,v2`: очередь возвращается к первому указанному шоту, повторяет оставшиеся
  порции с докачкой и все последующие проверки. Обычный `retry` повторяет только упавший шаг.
- Нужно изменить сценарий/код/монтаж — `cancel JOB`, внеси правки в исходную копию, согласуй их и отправь новое
  задание. `resume` и `retry` используют прежний снимок. Старые кадры другого задания не подмешиваются в новый.
- При обрыве SSH текущая порция на rinat-pc продолжает работать через Планировщик Windows. Координатор ждёт связь,
  узнаёт состояние по тому же id/номеру шага и забирает результат. Отключённый remote не превращается в «успех»
  и не запускает те же кадры на другом ПК. Отмена при недоступном remote ждёт подтверждения остановки после связи.
- `stop` завершает worker **после текущих порций**; очередь остаётся на диске. `start` продолжает её. После
  перезагрузки worker продолжает при входе пользователя в Windows, либо через `start`/следующий `submit`.
  Без пользовательского входа локальный worker не работает. Если координатор аварийно завершился, ресурс дополнительно защищён проверкой
  процессов; живой дочерний процесс TTS/сборки также записан в lock. Готовые кадры и курсор сохраняются.
  Старые файловые блокировки ОС снимаются самой ОС.
- Закрытие окна чата не отменяет очередь. Для отмены используй `cancel`, а не убийство верхнего bash/Python.
- Состояния: `queued`, `running`, `paused`, `failed`, `cancelled`, `needs_review`, `done`.

## Другие операции Blender и совместимость

Разовая проверка, замер, storyboard `draft`, регресс или собственная сборка тоже идут через шлюз:

```bash
python tools/render_queue.py submit task episodes/<ep>/episode.json --script episodes/<ep>/shots_9x16.py --args v1 draft
```

`--args` ставится последним. `task` выполняется локально; скрипт и его входы должны находиться в снимке, а вывод —
в `out/<ep>/`. Для `task … final` также нужна запись уже полученного одобрения. Для штатного финала используй
`submit final`, чтобы автоматически пройти звук, сборку и QA. Не запускай Blender/TTS/music/mix вручную в обход
очереди: внешние процессы проверяются, но два некоординируемых прямых запуска не могут дать атомарную гарантию.

`render_episode.sh` теперь ставит `frames` в очередь и требует `--approved`. `remote_render.py start --ep EP
--approved '…'` — совместимый вход в `frames --target remote`. `frames` делает только кадры + framecheck.
`push/start/pull` из старого процесса не нужны для новой очереди: она отправляет снимки и забирает результаты сама.
`remote_render.py setup/check/free/status/pull/stop` оставлены для диагностики и **старых** рендеров. Их `status`
не показывает прогресс новой очереди — используй `render_queue.py status`. Прямой `remote/agent.py start` отключён.

Проверка механики без GPU и сети: `python -m unittest discover -s tests -v`.
