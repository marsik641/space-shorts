# Рендер на другом ПК (по ssh)

**Новые задания отправляются через `tools/render_queue.py`** — `docs/render_queue.md`. Очередь сама отправляет
изолированный снимок и забирает кадры; ручной выбор ПК, `push` и `pull --watch` не нужны. Этот документ сохраняет
настройку SSH/ПК и диагностику старого транспорта. `start` теперь ставит кадры в очередь и требует явные
`--ep EP --approved 'одобрение из чата'`. Статус новой очереди — `render_queue.py status`.

Финальный рендер можно гнать на чужом ПК: этот ПК свободен, кадры по сети приходят сюда, дальше конвейер как
обычно (звук, монтаж, QA, пакет). Инструменты: `tools/remote_render.py` (здесь), `tools/remote/agent.py` (там),
`tools/remote/setup_remote_pc.ps1` (разовая настройка того ПК).

## Что нужно от удалённого ПК

| | Требование | Зачем |
|---|---|---|
| ОС | Windows 10/11 (под ней проверялось; Linux тоже поддержан агентом) | шрифты подписей в кадре (Bahnschrift, Segoe UI) — из Windows |
| GPU | NVIDIA RTX (OptiX), 8+ ГБ видеопамяти — как здесь; иначе CUDA/AMD/CPU — медленнее, денойзер другой | одинаковый вид кадров |
| Blender | **5.2.x** (лучше ровно 5.2.2, как здесь), на любом диске — агент ищет на C:…H: (или `--blender`) | API Blender 5 |
| Python | 3.8+ с python.org (не из Microsoft Store), в PATH (`python --version`) | агент — только стандартная библиотека; Store-версия плохо запускается из Планировщика |
| Диск | ≥ 15 ГБ свободно на диске рабочей папки — по умолчанию **D:\orbitfall** (на C: место не нужно) | ~6–7 ГБ PNG на ролик + запас |
| Сеть | Tailscale (бесплатный VPN) на обоих ПК; отдача у друга желательно ≥ 10 Мбит/с | ~6 ГБ кадров обратно, качаются частями прямо во время рендера |
| Режим | ПК включён, пользователь залогинен (экран можно заблокировать); во время рендера не играть на этом GPU | рендер идёт задачей Планировщика в сеансе пользователя; сон на время рендера блокирует агент |

## Что сделать тебе и другу (один раз, ~15 минут)

1. **Tailscale на оба ПК** (https://tailscale.com/download): войти в один аккаунт **или** другу — своим аккаунтом,
   и расшарить свой ПК тебе (admin console → Machines → Share). Проброс портов на роутере не нужен.
2. **На ПК друга** скачать `tools/remote/setup_remote_pc.ps1` (ты пришлёшь файл) и запустить в PowerShell **от имени
   администратора**: `powershell -ExecutionPolicy Bypass -File setup_remote_pc.ps1`. Скрипт включит встроенный
   OpenSSH Server, добавит один публичный ключ (вход только по нему, пароли не передаются), создаст рабочую папку
   `D:\orbitfall` (другой диск: `-Root E:\orbitfall`) и напечатает сводку.
3. **Прислать мне сводку** скрипта: `user`, `tailscale` (адрес 100.x.y.z), `blender`, `gpu`, свободное место.
4. Перед рендером другу — не выключать ПК, не уводить в сон, не играть на GPU.

Отозвать доступ: удалить строку `orbitfall-render` из двух файлов ключей (их пути печатает скрипт) или остановить
службу: `Stop-Service sshd; Set-Service sshd -StartupType Disabled`.

### Tailscale рядом с прокси (FlClash / Clash Meta) — прокси не выключать

Tailscale — не «VPN в интернет»: он ведёт через себя только адреса 100.x (связь двух ПК), весь остальной трафик идёт
как раньше через прокси. Конфликт бывает только с TUN-режимом прокси: он перехватывает пакеты самого Tailscale. Лечится
правилами обхода — **на обоих ПК**, в FlClash: Профили → ⋮ у профиля → Переопределение (Override) → Правила → добавить
**в начало** (выше правил подписки):

```
IP-CIDR,100.64.0.0/10,DIRECT,no-resolve
IP-CIDR6,fd7a:115c:a1e0::/48,DIRECT,no-resolve
PROCESS-NAME,tailscaled.exe,DIRECT
PROCESS-NAME,tailscale-ipn.exe,DIRECT
```
Если в настройках TUN есть список исключений маршрутов (route-exclude / bypass) — добавить туда `100.64.0.0/10`.
Если Tailscale не логинится (сайт недоступен напрямую) — первой строкой ещё
`DOMAIN-SUFFIX,tailscale.com,<имя вашей группы прокси>`: вход и ретрансляторы пойдут через прокси, а данные между ПК —
напрямую.

Проверка на твоём ПК: `tailscale status` (виден ПК друга), `tailscale ping <имя ПК друга>` → `pong … via <ip:port>`
— прямая связь, кадры пойдут быстро; `via DERP(…)` — через ретранслятор Tailscale, работает, но медленнее
(6 ГБ кадров могут идти часами). Аккаунты: проще всего обоим войти в твой аккаунт Tailscale; аккуратнее — друг
входит своим и делится ПК с тобой (admin console → Machines → ⋯ → Share → твоя почта).

Проверено 18.10.2026 (mtj ↔ rinat-pc):
- Правила нужны только на том ПК, где прокси в TUN-режиме ловит трафик Tailscale. Признаки: у этого ПК в
  `tailscale status --json` пустые `Addrs`, `tailscale ping` молчит даже через DERP, а `tailscale netcheck` (сам CLI
  идёт через прокси) показывает чужой IPv4 — адрес выхода прокси. На mtj FlClash работает без правил.
- Через прокси Tailscale выбирает ближайший к выходу прокси DERP. У rinat-pc это был Helsinki (серверы Hetzner), а
  он с российского провайдера mtj напрямую недоступен (TCP-таймаут) — пакеты не доходили. С выключенным прокси
  у друга: `pong via DERP(waw)`, ssh работает.
- Если после добавления правил пропадает доступ к другим сайтам — правила профиля **заменились**, а не дополнились.
  Нужно добавлять свои строки к правилам подписки, не вместо них. Иначе на время рендера и скачивания кадров
  просто выключить прокси на ПК-рендерере.

## Два ПК: какой свободен

Рендер-ПК два: этот (mtj) и rinat-pc. **Выбирает очередь** (`docs/render_queue.md`): `auto` предпочитает свободный
rinat-pc, иначе этот ПК; первый шаг рендера закрепляет ПК за заданием. Вручную ПК не выбирать. Диагностика:

```bash
python tools/remote_render.py free     # последняя строка: FREE remote <host> | FREE local | BUSY
python tools/render_queue.py status     # что и где считается сейчас
```
- этот ПК занят — lock очереди или любой `blender.exe`;
- rinat-pc занят — там идёт порция задания; не отвечает по ssh — у друга включён прокси или ПК спит (очередь ждёт
  связь и не переносит начатое задание на другой ПК);
- снимок кода фиксируется на задание, поэтому правки `spacekit/` в своей worktree не попадают в чужой рендер.
  На rinat-pc кадры эпизодов лежат в `D:\orbitfall\out\<ep>\` (на D: ~455 ГБ, ~6–7 ГБ на ролик).

## Что делаю я (команды здесь, Git Bash)

```bash
python tools/remote_render.py setup --host <user>@<100.x.y.z>   # папка D:/orbitfall (--root); код + ассеты, проверка
python tools/remote_render.py start --ep EP --approved 'одобрение из чата' # кадры явного эпизода через очередь
python tools/remote_render.py status                                # кадры там/здесь, ошибки, оценка времени
python tools/remote_render.py pull --watch                          # каждые 5 мин забирает кадры; все — framecheck
python tools/remote_render.py stop                                  # остановить (докачка: start продолжит)
python tools/remote_render.py free                                  # какой ПК свободен: этот или удалённый
```
Старый транспорт (до очереди): после правки шотов или библиотеки — `push` (заливает код заново, готовые кадры там не
трогает; кадры изменённых шотов удалить там и здесь). В очереди кадры ложатся в снимок `out/q/<JOB>/`, в `out/<ep>/`
— по завершении задания; дальше финал очереди сам проходит звук, сборку, QA и release (`docs/pipeline.md`, этап 3).

## Как устроено

- Связь — обычный ssh с отдельным ключом `~/.ssh/orbitfall_render` (`remote_render.py keygen`); настройки
  (host, папка, python) после `setup` хранятся в `out/remote.json`.
- Агент там запускает рендер задачей Планировщика `OrbitfallRender`: не умирает при обрыве ssh, без окон
  (pythonw + blender без консоли), шоты по очереди, докачка, один повтор шота при ошибке, логи
  `D:\orbitfall\out\logs\<ep>\render_<шот>.log`, статус `out\remote_status.json`.
- Устройство Cycles — первое доступное: OptiX → CUDA → HIP → oneAPI → Metal → CPU (`spacekit.render.pick_device`,
  переопределение: `start --device CUDA`). Денойзер: OptiX на NVIDIA, иначе OIDN — поэтому шоты одного ролика
  рендерить на одной машине.
- Кадры забираются tar-пачками по 300 (только дописанные PNG, проверка сигнатуры и IEND), битые удаляются и
  перекачиваются на следующем проходе. Каждый проход `pull` забирает и логи `render_<шот>.log` в
  `out/logs/<ep>/` — из них `tools/cues.py` берёт FLASH/EVENT.
- Строки `print` из скрипта шота (`[render] device …`, FLASH/EVENT) Blender пишет в лог только при выходе из шота
  (буфер Python; переменные PYTHON* встроенный Python Blender игнорирует), а строки `Saved: …` — сразу.
- Python 3.15+ по умолчанию читает вывод программ как UTF-8, а `tasklist`/`schtasks` в русской Windows пишут в
  cp866 — агент читает их вывод байтами.
- Сбой ep002 (18.10.2026): на rinat-pc в v1 подряд 31 кадр (135–165) вышел с другим светом — антенна без солнечного
  света, ошибок в логе нет, время кадра обычное. Повторный рендер тех же кадров здесь — чистый, т. е. сбой разовый
  (GPU/драйвер), не сцена. Ловится по скачку размера PNG на ±5 % при фоне ±0,1 % (так же видны задуманные события —
  «восход» v2 f27). Найден был только глазами на мастере — пришлось пересобирать.
- Поэтому `pull`, когда пришли все кадры (с `--shots` — этих шотов), сам запускает `tools/framecheck.py`
  (`docs/pipeline.md`, «QA»): целость PNG и скачки размера вне FLASH/EVENT из забранных логов. FAIL — код выхода 1
  и строки `RERENDER <шот>: a–b`: удалить эти кадры здесь и в `D:\orbitfall\out\<ep>\9x16\frames\<шот>\`, `start`
  (докачка дорендерит только их) и `pull`; кадры, удалённые только здесь, `pull` скачает обратно те же битые.
